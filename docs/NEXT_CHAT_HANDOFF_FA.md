## روش صحیح دیپلوی

سرور یک Deploy Key مجزای GitHub با دسترسی نوشتن دارد:

`/root/.ssh/valyria_github_write`

اگر پوش مستقیم از ویندوز به‌دلیل Credential Manager خراب شد، تغییرات را ابتدا کامیت کن، با Git bundle به سرور بفرست و آنجا fast-forward کن. سپس هر دو image را build و اجرا کن:

```bash
cd /opt/valyria/app
docker compose build backend frontend
docker compose up -d backend frontend
docker compose ps
docker compose logs --tail=80 backend
curl -fsS https://valyria-game.duckdns.org/api/health
```

پوش از VPS به GitHub:

```bash
GIT_SSH_COMMAND='ssh -i /root/.ssh/valyria_github_write -o IdentitiesOnly=yes' git push origin new-design
```

در پایان، هش سرور و GitHub باید یکسان باشند:

```bash
git rev-parse HEAD
GIT_SSH_COMMAND='ssh -i /root/.ssh/valyria_github_write -o IdentitiesOnly=yes' git ls-remote origin refs/heads/new-design
```

## تست و کنترل کیفیت

وابستگی npm ویندوز در آخرین اجرا خراب بود و `npm-cli.js` پیدا نمی‌شد. build معتبر فرانت داخل Docker سرور انجام شد.

تست‌های بک‌اند داخل کانتینر:

```bash
docker compose exec -T backend python -m unittest discover -s tests -v
```

در آخرین اجرا ۱۷ تست با موفقیت پاس شدند. پیش از تحویل هر تغییر مهم:

1. `python -m compileall backend`
2. `git diff --check`
3. build فرانت و بک‌اند در Docker
4. اجرای تست‌های بک‌اند داخل کانتینر
5. بررسی health endpoint و لاگ‌های backend
6. تطبیق هش سرور و GitHub

## آخرین تغییرات انجام‌شده

### رول جنگ پس از حرکت دوبارهٔ لشکر

فهرست نبردهای قابل رول اکنون از پروندهٔ باز نبرد و `battle_participant_tg_ids` استخراج می‌شود. لشکری که بعد از نتیجهٔ قبلی دوباره حرکت کرده و وارد نبرد تازه شده، باید بتواند برای نبرد جدید رول ارسال کند.

### اعلان عمومی آغاز نبرد

اعلان عمومی برای بازیکنان نوع دقیق نیرو یا ادوات را فاش نمی‌کند، اما برای هر لرد این موارد را نشان می‌دهد:

- مجموع نفرات
- مجموع ادوات

ادمین همچنان ترکیب دقیق نیروها، ادوات و سناریوها را دریافت می‌کند.

### مسیر کاروان

در ارسال کاروان حداکثر سه مسیر پیشنهاد می‌شود. هر مسیر جداگانه بررسی می‌شود و اگر مجوز عبور نداشته باشد، نام لردهای مشکل‌دار نمایش داده می‌شود.

- مجوز معتبر: پیمان تجاری یا اتحاد کامل پذیرفته‌شده
- پیمان عدم تجاوز برای کاروان معتبر نیست
- مسیر انتخاب‌شده در بک‌اند نیز دوباره اعتبارسنجی می‌شود

### موجودی اعشاری و هزینهٔ برابر

تولید منابع در دیتابیس اعشاری ذخیره می‌شود ولی `/me` مقدار را گرد می‌کند. قبلاً ممکن بود بازیکن `11` چوب ببیند ولی مقدار خام `10.8369` باشد و هزینهٔ ۱۱ رد شود.

توابع مشترک `can_afford` و `pay` اصلاح شدند تا موجودی قابل خرج با عدد نمایش‌داده‌شده یکسان باشد و هیچ موجودی منفی ایجاد نشود.

### برنده‌های مختلط در نبرد گروهی

ادمین اکنون می‌تواند از هر دو ستون فنی مهاجم و مدافع هم‌زمان برنده انتخاب کند. این قابلیت برای ائتلاف‌های پیچیده و کمک یک لشکر مهاجم به صاحب قلعه لازم است.

- هر برنده طبق سمت واقعی خودش امتیاز، آمار و محبوبیت می‌گیرد.
- هر فرد درگیر که انتخاب نشده باشد بازنده محسوب می‌شود.
- جریمهٔ بازنده نیز طبق سمت واقعی خودش محاسبه می‌شود.
- نتیجهٔ مختلط با `combat_outcome = "mixed"` ذخیره می‌شود.
- تلفات همچنان برای هر لشکر جداگانه ثبت می‌شود.

## قواعد مهم محصول

- ادمین‌ها بازیکن نیستند، قلعه و خاندان ندارند و در جدول امتیازات نیستند؛ با این حال باید بتوانند محیط عادی بازی و کلاغ را ببینند.
- سه نقش ادمین وجود دارد:
  - ادمین اصلی: تمام دسترسی‌ها و امکان ساخت ادمین اصلی دیگر
  - ادمین کامل: همهٔ تب‌ها به‌جز مدیریت ادمین‌ها
  - ادمین اجرایی: فقط امور داوری و ارتباط
- تمام نتیجه‌های نبرد باید یک پروندهٔ یکپارچه داشته باشند.
- لشکر در نبرد باز تا ثبت نتیجه یا انحلال نبرد قفل می‌ماند.
- نبرد گروهی ممکن است چند برنده از سایدهای مختلف داشته باشد.
- اطلاعات دقیق یگان‌ها فقط برای طرفین و ادمین است؛ اعلان عمومی فقط مجموع نفرات و ادوات را نشان می‌دهد.
- پیام نتیجهٔ نبرد باید نام نبرد، طرفین، محل، متن داوری، برنده‌ها، بازنده‌ها، تلفات و بازمانده‌ها را منظم نمایش دهد.
- کاروان برای تمام صاحبان قلعه‌های مسیر به پیمان تجاری یا اتحاد کامل نیاز دارد.
- UI باید موبایل‌محور، فارسی، RTL و هماهنگ با طراحی فعلی باشد.

## نکات احتیاطی برای ادامه

- پیش از اصلاح باگ‌های نبرد، ارتباط میان `campaigns`، شناسهٔ `engagement_campaign_id`، ریشهٔ نبرد، آرایه‌های لشکرهای دو طرف، رول‌ها، قفل‌ها و اعلان‌ها با هم بررسی شود.
- در تغییر نتیجهٔ نبرد فقط UI کافی نیست؛ اعتبارسنجی بک‌اند، پاداش، محبوبیت، مدال، تلفات، آزادسازی لشکرها و پیام نهایی هم باید هماهنگ تغییر کنند.
- اطلاعات واقعی سرور را می‌توان به‌صورت read-only بررسی کرد، اما دیتابیس بدون درخواست روشن کاربر دستکاری نشود.
- فایل `.env` موجود روی سرور حفظ شود و در Git قرار نگیرد.
- پس از تغییر فرانت، فقط ری‌استارت backend کافی نیست؛ image فرانت نیز باید rebuild و recreate شود.
- پس از تغییر backend نیز صرفاً `git pull` کافی نیست؛ کانتینر باید rebuild شود.
